# SecondPart Android Release Permission Policy

Snapshot: 2026-09-10
Production package: `com.secondpart.marketplace`

This document defines the Android permission guard used by the production-style and real Production AAB pipelines.

The guard examines the **merged Release AndroidManifest**, after Capacitor and native plugins have contributed their manifest entries. It does not rely only on SecondPart source manifests.

## Product principle

SecondPart should request only permissions needed for a visible marketplace feature. A dependency or future SDK must not silently introduce sensitive Android access simply because the application can technically declare it.

Current product behaviour uses:

- internet/network access for the hosted Next.js marketplace and APIs;
- camera/photo selection for seller listing/evidence images;
- push notification capability for opted-in marketplace notifications;
- Android application lifecycle/native navigation capabilities.

Current marketplace distance is postcode-based. **SecondPart does not require device GPS/location permission.**

Sleep/audio recording, contacts, SMS, call history, health/body sensors, broad installed-app inventory and unrestricted external-storage management are not part of the current product.

## Release-blocked permissions

The Release manifest verifier fails if any of these permission families appear without an explicit product/security review and corresponding update to this policy, Privacy Policy and Google Play Data Safety answers.

### Location

- `android.permission.ACCESS_FINE_LOCATION`
- `android.permission.ACCESS_COARSE_LOCATION`
- `android.permission.ACCESS_BACKGROUND_LOCATION`

Reason: marketplace proximity is currently postcode-based; device location is unnecessary.

### Microphone/audio capture

- `android.permission.RECORD_AUDIO`

Reason: SecondPart does not currently record audio.

### Contacts/accounts

- `android.permission.READ_CONTACTS`
- `android.permission.WRITE_CONTACTS`
- `android.permission.GET_ACCOUNTS`

Reason: no contact-book feature exists.

### SMS

- `android.permission.READ_SMS`
- `android.permission.SEND_SMS`
- `android.permission.RECEIVE_SMS`
- `android.permission.RECEIVE_MMS`
- `android.permission.RECEIVE_WAP_PUSH`

Reason: SecondPart does not read or send device SMS/MMS.

### Phone/call history

- `android.permission.READ_CALL_LOG`
- `android.permission.WRITE_CALL_LOG`
- `android.permission.READ_PHONE_STATE`
- `android.permission.READ_PHONE_NUMBERS`
- `android.permission.CALL_PHONE`
- `android.permission.ANSWER_PHONE_CALLS`

Reason: no telephony/call-history product feature exists.

### Health/body/activity sensors

- `android.permission.BODY_SENSORS`
- `android.permission.BODY_SENSORS_BACKGROUND`
- `android.permission.ACTIVITY_RECOGNITION`

Reason: not relevant to an automotive-parts marketplace.

### Calendar

- `android.permission.READ_CALENDAR`
- `android.permission.WRITE_CALENDAR`

Reason: the current product does not read/write the user's device calendar.

### Broad storage / package / overlay access

- `android.permission.MANAGE_EXTERNAL_STORAGE`
- `android.permission.REQUEST_INSTALL_PACKAGES`
- `android.permission.QUERY_ALL_PACKAGES`
- `android.permission.SYSTEM_ALERT_WINDOW`
- `android.permission.PACKAGE_USAGE_STATS`

Reason: these are materially broader than current marketplace requirements.

### Nearby device scanning

- `android.permission.BLUETOOTH_SCAN`
- `android.permission.BLUETOOTH_CONNECT`
- `android.permission.BLUETOOTH_ADVERTISE`
- `android.permission.NEARBY_WIFI_DEVICES`

Reason: no Bluetooth/nearby-device discovery feature exists.

## Permissions that may legitimately appear

The verifier intentionally does not use a narrow allow-list because Android/Google/Firebase/Capacitor can add low-risk implementation permissions across SDK versions. Examples that may be legitimate include:

- `android.permission.INTERNET`
- `android.permission.ACCESS_NETWORK_STATE`
- `android.permission.CAMERA`
- `android.permission.POST_NOTIFICATIONS`
- Firebase notification/service delivery permissions such as wake/receive/vibration capabilities where generated by the approved dependency set.

Their appearance still has to be reviewed in the generated permission report before Play submission.

## Generated release evidence

`scripts/verify-android-release-manifest.mjs` searches Gradle's generated Release manifest outputs after `bundleRelease`, extracts declared `uses-permission` entries, checks the forbidden set above and writes:

```text
android-release-permissions.txt
```

The report includes:

- detected merged-manifest path;
- production package expectation;
- sorted declared permissions;
- explicit statement that no blocked sensitive permission was found.

The production workflow stores this report next to the AAB release artifact so the exact permission inventory can be compared with Google Play Data Safety answers.

## Change rule

If a future feature genuinely needs one of the blocked permissions:

1. define the user-facing feature and why the permission is necessary;
2. prefer a less invasive Android/API design if one exists;
3. update this policy deliberately;
4. update Privacy Policy and Data Safety inventory;
5. add permission UX/rationale and denial-path testing to the Android RC matrix;
6. run the production-style AAB pipeline and physical-device RC again.

Do not simply remove a permission from the blocked list to make CI green.
