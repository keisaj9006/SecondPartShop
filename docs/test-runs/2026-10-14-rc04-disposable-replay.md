## Disposable replay result

`scripts/rc04-disposable-replay.mjs` builds the manifest from the RC-02 matrix and applies each unit in a transaction to a new in-memory PostgreSQL instance, stopping on the first failure and recording every file hash. Its clean-state check rejects pre-existing public tables. The runner normalizes CRLF to LF before SQL execution while retaining the source hash; this lets the historical fail-closed `pg_get_functiondef` patch find its exact LF fragment. To pass Supabase platform prerequisites in PGlite, it creates explicit **disposable** Auth, Storage and Cron shims and reproduces Preview's public default grants. pgcrypto and pg_trgm use PGlite's extension bundles. The sole non-transport SQL adaptation strips the unavailable `CREATE EXTENSION pg_cron` statement at one pinned file and records both source and executed hashes. Cron scheduling semantics and Supabase Auth/Storage behaviour are **not** validated by this shim.

The final package applied **207/207 units on two fresh disposable instances** with the same results. The [machine log](2026-10-14-rc04-replay-log.json) records the ordered source/execution SHA-256 hashes, final catalog, category fingerprint, candidate application twice, and rollback readback. This is **PASS for the PGlite replay with documented shims**, and **EXTERNAL for a native PG17.6/Supabase replay**. The full-source `pg_get_functiondef` guard remained enabled; the earlier 196-unit stop was solely a CRLF/LF transport mismatch in the local runner.

## Review-ready rehearsal

The full-schema disposable replay applied `20261014202700_review_ready_notifications_forward.sql` **twice** after baseline, then verified exactly one function, one trigger and the existing dedupe index. Candidate SQL SHA-256 after LF normalization: `de915d37becb9bbecfcc99edf9c6ca220284c85673bb5c6ff3b6bf3d61f5ab94`. A local rollback removed the function/trigger and restored their counts to zero. `scripts/test-rc04-review-ready-sql.mjs` separately uses synthetic orders/items to confirm the AFTER UPDATE trigger is attached to the three intended columns; no notification before all three conditions (`completed`, `released`, non-null release timestamp); both buyer and seller receive the expected account notification when release or completion is the last transition; no third-party recipient; an existing buyer dedupe key yields only the missing seller row; repeated updates, retry transitions and payout reversal do not duplicate notifications. The function is `SECURITY DEFINER`, has empty `search_path`, and is not directly executable by anon or authenticated. The rollback rehearsal retains already-created notifications and stops future ones. **Existing already-eligible items receive no retroactive notification** because the migration has no backfill and its trigger runs only on a later qualifying field transition. Any historical backfill would require a separate approved design and data-impact review. No existing account/order was touched.

## Deployment plan — only after a later explicit approval

1. Reproduce all **207 manifest units from zero twice** on PostgreSQL 17.6 with native Supabase Auth, Storage, pgcrypto, pg_trgm and pg_cron; no shims or skipped SQL. Prove clean-state reset and capture every unit hash, final function/trigger/policy/grant fingerprint and scheduled Cron jobs. Investigate any native-only failure before proceeding.
2. Diff the native disposable catalog against fresh Preview SELECT-only readback for all 188 application functions, 50 triggers, 135 policies, category fingerprint, critical table grants, extension jobs and notification constraints. Treat any unexplained difference as a blocker. Re-run the review-ready candidate on the full native disposable schema, including the synthetic transition matrix and rollback.
3. Before any hosted write, capture a fresh Preview backup/snapshot and ledger head, check that the five-function repair still has version/name `20261008130523_account_deletion_checkout_fitting_serialization`, and check that candidate function, trigger and ledger version `20261014202700` remain absent. Pin the exact reviewed SQL SHA-256. Choose and document a **single-migration deployment mechanism that records exactly the intended new version/name without attempting to replay the four historical collisions**. Ordinary `db push` is not safe while the ledgers diverge. Obtain explicit approval of the exact SQL, project, migration identity and maintenance window.
4. Apply only `20261014202700_review_ready_notifications_forward.sql` as one reviewed migration on the authorized Preview target, never on Production. Then read back function/trigger definition, grants, RLS/index preconditions, ledger row and deployment logs. Observe real notification outcomes through read-only monitoring; do not create synthetic financial transitions on the shared host.
5. If the new trigger malfunctions, disable it through a **new approved forward rollback migration** after confirming no other dependency uses the function. The reviewed rollback body is:

   ```sql
   begin;
   drop trigger if exists transaction_review_ready_notification on public.order_items;
   drop function if exists private.notify_transaction_review_ready();
   commit;
   ```

   Keep already-issued notifications as an audit trail, monitor for duplicates, and issue a separately reviewed corrective data action only if real evidence requires it. Do not delete ledger rows or run migration repair. Reapplying the candidate after rollback requires another reviewed forward migration and fresh preflight.
