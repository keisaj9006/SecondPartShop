## Task 2: Make seller photo removal safe across database and Storage

**Requirement:** Close SEC-01 without weakening reservation, last-active-photo or privacy deletion guarantees. Read the bounded design review in `.superpowers/sdd/2026-09-11-marketplace-integrity/sec-design-review.md` for the established races. This repairs existing guarantees; it does not change the product model.

**Scope:** one new CLI-generated migration; web listing actions; mobile seller photo route; a focused server-only cleanup module; current maintenance and account-deletion workers; relevant database types; regression tests and a runbook. No package/CI changes, provider mutations, commits or subagents by implementer. Controller handles those gates. Work only on rebuild-nextjs, never main/Production/Stripe Live.

1. Add red tests at the real web/mobile action and cleanup-worker boundaries: reserved and unauthorized or RLS-zero-row deletes must never remove bytes; metadata failure must never remove bytes; successful authorized deletion queues the exact owned path; Storage failure preserves retry intent; repeat success/absent-object removal is harmless. Cover failed-upload cleanup using only the server-generated path, not caller-supplied arbitrary paths.
2. Use a small private durable cleanup outbox with unique exact path, owner/seller context, created/completed timestamps. No client table grants; only narrowly scoped service-role queue/worker RPCs. Preserve ownership context through account deletion, with no cascading loss of pending work. Keep completed-path protection until the owner identity is safely deleted; remove identifying tombstones at privacy finalization, with retries preserved.
3. Strengthen metadata deletion in a DB trigger: lock the owning `parts` row before checking status/count; reject authenticated reserved edits and deleting the final active photo; insert the cleanup intent atomically with metadata removal. Existing service/admin privacy and retention operations retain their authority. Ensure direct authenticated table deletion gets the same guarantees as the application. Parent locking must serialize with checkout. Lock/guard image attachment and storage-path changes too: a pending/completed cleanup path cannot be attached again; path must belong to the authenticated owner and exact part; part ID/storage path immutable on existing rows (position/alt edits allowed). Address concurrent orphan queueing versus attachment with a consistent lock ordering.
4. Deny direct authenticated Storage DELETE/UPDATE for part-images once all existing app cleanup paths have been routed through the validated service worker. Retain normal unique-path upload (`upsert:false`) and reads. No SQL mutations of storage objects. Worker removes bytes using Storage API only after durable authorization exists; a missing/failed RPC must fail closed. Existing account-deletion service authority remains intact.
5. Web/mobile photo deletion performs the authorized metadata mutation first and confirms an actual returned row before attempting queued cleanup. Early reserved guards provide understandable UI/API errors. Upload-attachment failures enqueue only the generated owned path and safely attempt cleanup. Keep genuine mutation failures visible; a transient cleanup failure after successful metadata deletion stays queued and is reported safely without suggesting the image is still attached.
6. Reuse current maintenance scheduling for bounded cleanup retries. Extend account-deletion path discovery/processing to pending cleanup and ensure incomplete Storage cleanup prevents privacy completion. Cover resumed deletion after identity detachment. No new scheduled paid service.
7. Tests: run red/green Node tests plus meaningful migration contract guards, lint/typecheck; document where real database concurrency tests remain needed. Write disposable, transaction-rollback SQL QA scenarios for parent locking / last-photo / retired-path ownership where practical, but do not execute provider writes yourself. Include rollback/rollout order: DB authority and app must be compatible; no temporary policy gap. If backwards compatibility needs two migrations (expand then enforce), explicitly separate them for controller to apply in safe order.
8. Check actual existing callers before removing any policy. Do not add unrelated cover reordering, visual redesign, checkout behavior or speculative optimization. Report concerns rather than silently widening scope. Leave changes uncommitted with full report at `.superpowers/sdd/2026-09-11-marketplace-integrity/task-2-report.md`.

Controller gates: independent spec/security review; all Node tests, web checks and commerce/privacy/monitoring validators; inspect live baseline policies; verify database controls with disposable QA only; Preview browser add/delete photo and upload-failure behavior where safe; exact-HEAD CI/deployment and aliases; then continue NAV-01/NAV-02/API-01 in the next plan batch.
